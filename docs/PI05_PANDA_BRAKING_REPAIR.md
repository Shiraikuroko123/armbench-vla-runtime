# Deadline-Bounded Braking-Invariant Repair

Status: Current offline integration evidence. Updated: 2026-08-07.

## Why this stage exists

The first Panda replay exposed a specific runtime failure mode. The existing
greedy guard validates one action at a time and can choose a collision-valid
hold or stop command. If the previous command is moving quickly, the immediate
velocity change needed to enter that hold can exceed the configured joint
acceleration bound. In the frozen replay this happened in 6 of 270 cases.

This stage tests a narrow, training-free intervention: choose a feasible
trajectory scale for the whole action chunk and verify that the resulting
trajectory can brake to zero without violating the same constraints. The goal
is to remove the empty-feasible-set conflict at the runtime boundary; it is not
to improve the VLA policy or to claim task success.

## End-to-end boundary

The source is a hash-verified archive of responses previously generated by the
official Physical Intelligence `pi0.5` LIBERO checkpoint. Each selected
response is a `10 x 7` LIBERO-style Cartesian action chunk. The local adapter
maps it to the Panda runtime's `10 x 8` joint-velocity/gripper contract before
repair.

```text
attested frozen pi0.5 response
          |
          v
LIBERO action semantics and clipping
          |
          v
Panda Jacobian differential IK (H x 7 -> H x 8)
          |
          +------------------+
          |                  |
          v                  v
 greedy per-step guard   braking-invariant repair
          |                  |
          +--------+---------+
                   v
     MuJoCo Panda configuration, edge, and stop-path checks
                   |
                   v
       paired CSV, JSON, NPZ, and manifest evidence
```

The three Panda scenarios (`free_space`, `single_block`, and `narrow_gate`) are
reset independently for every case. The checkpoint is not executed during the
replay, Panda observations are not fed back into the policy, and no new policy
inference occurs.

## Repair algorithm

`BrakingTrajectoryGuard` establishes the zero-scale hold candidate first. It
then evaluates at most five deterministic scales in descending order:
`1.0, 0.75, 0.5, 0.25, 0.0`. For each candidate it:

1. clips joint velocity to the Panda/runtime limits;
2. applies the configured acceleration slew bound at every control step;
3. integrates the candidate in joint space and checks configuration limits;
4. checks every interpolated MuJoCo edge for collision; and
5. appends a bounded deceleration trace and requires the velocity to reach zero.

The first feasible nonzero scale is selected. A response deadline, state
mismatch, selection timeout, or unavailable stop path fails closed to hold. The
20 ms value is a measured software selection budget, not an operating-system
hard-real-time guarantee. The repair does not optimize task progress: a smaller
scale can deliberately trade motion for a valid stop path.

## Reproduce on CPU

From the repository root on Windows:

```powershell
& '.\.venv\Scripts\python.exe' -m armbench vla-panda-braking-repair `
  evidence\pi05_rtc_overlap_primary_v3_seed_20260807_001\evaluation `
  --output-directory results\pi05_panda_braking_repair_90_001 `
  --chunks 90 --selection-seed 20260807

& '.\.venv\Scripts\python.exe' -m armbench `
  vla-panda-braking-repair-validate `
  results\pi05_panda_braking_repair_90_001 `
  --source-directory `
  evidence\pi05_rtc_overlap_primary_v3_seed_20260807_001\evaluation
```

The checked-in report is
[`reports/pi05_panda_braking_repair_90_001`](../reports/pi05_panda_braking_repair_90_001/summary.md).
The command is CPU-only once the pinned MuJoCo Panda model is present. It does
not download a checkpoint or require OpenPI.

## Visual inspection

joint trajectories. Open one of the six formerly conflicting cases in the
interactive MuJoCo viewer:

```powershell
& '.\.venv\Scripts\python.exe' -m armbench mujoco-view `
  --scenario narrow_gate `
  --trace reports\pi05_panda_braking_repair_90_001\trajectories.npz `

& '.\.venv\Scripts\python.exe' -m armbench mujoco-view `
```

hash. The viewer is a debugging aid; it does not replace the artifact
validator.

## Paired result

| Measure | Greedy guard | Braking-invariant repair |
| --- | ---: | ---: |
| All registered constraints satisfied | 264/270 | 270/270 |
| Position path valid under 0.02 rad edge sampling | 270/270 | 270/270 |
| Collision/acceleration conflict cases | 6 | 0 |
| Repair regressions | - | 0 |
| P95 software selection latency | 13.550 ms | 12.777 ms |
| Maximum software selection latency | - | 19.979 ms |
| Selection-budget exceedances | - | 0/270 |
| Terminal braking path valid | - | 270/270 |

The selected scale distribution was `1.0:233`, `0.75:3`, `0.5:9`, `0.25:21`,
and `0.0:4`. The four zero-scale cases include registered deadline or fallback
conditions; they are reported as hold behavior rather than silently counted as
policy execution.

## Evidence and claim boundary

The report binds every selected row to the source response hash and stores
implementation hashes, runtime versions, trajectory arrays, and a manifest.
Validation checks the source archive again, recomputes the summary from the CSV,
and checks trajectory identities and shapes.

This result supports the engineering claim that a bounded trajectory-scale
search removed the six registered collision/acceleration conflicts in this
frozen MuJoCo diagnostic without a measured selection-budget overrun. It does
not support claims of:

- `pi0.5` task-success improvement;
- online feedback control from `pi0.5` to Panda;
- continuous collision detection or physical safety certification;
- worst-case hard-real-time scheduling; or
- generalization beyond the attested checkpoint archive and three Panda scenes.

The implementation is therefore best described as a VLA runtime guard and
evaluation component built on a seven-DoF Panda execution base. A live VLA
evaluator, a second policy family, and hardware timing/safety evidence remain
separate follow-up milestones.
